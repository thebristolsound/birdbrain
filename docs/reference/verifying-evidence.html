Verifying Evidence

How a third party re-verifies a Birdbrain evidence package — with the standalone binary, or entirely by hand with stock tools.

In this set: Overview Exporting evidence Verifying evidence

An evidence package can be re-verified with no Birdbrain installation. There are two paths, which corroborate each other:

  • Path A — the standalone verifier binary (birdbrain-verify): a prebuilt, transparent executable that runs every check and prints a per-check PASS/FAIL report. Fast and non-technical-friendly.
  • Path B — by hand: the VERIFY.md runbook shipped in the package reproduces the full integrity claim with only sha256sum, openssl, and jq. This is the canonical path, and the only one that proves timestamp authenticity.

1. The trust model (read first)

  • manifest.jsonl is the root of trust. Each entry carries an entryHash and an RSA signature over that hash; entries are hash-linked (prevHash == the prior entry's entryHash) and index-ordered.
  • evidence.json is an unsigned convenience index. Do not trust it on its own — its integrity is established by re-deriving everything from the chain. Verification reconciles the index against the verified chain; it never lets the index decide what is true.
  • The signing key is installation-local (signing-public-key.pem ships inside the package). It defeats casual tampering but is not an independent trust anchor. The independent anchor for timestamped captures is the RFC 3161 timestamp, proven in step 6 by openssl ts -verify.
  • Binary-PASS ≠ runbook-PASS. The binary checks timestamp tokens structurally (imprint + byte binding); it does not verify the TSA's CMS signature. A forged token (correct imprint, invalid TSA signature) passes the binary and is caught only by the runbook's openssl ts -verify.

2. Path A — the standalone verifier binary

2.1 Obtain or build the binary

Use a prebuilt birdbrain-verify binary for your operating system if one is provided with the release. Otherwise build it from the repository (Node SEA produces a binary for the OS it runs on — build on the target OS):

pnpm build:verifier
# -> dist/verifier/birdbrain-verify        (birdbrain-verify.exe on Windows)

The binary is fs + crypto only — the build asserts that no Electron, database, native, or network import leaked into the bundle, so the verification tool carries none of the capture app's machinery. Build details are in §4.

2.2 Run it against an unzipped package

unzip evidence-package.zip -d ./pkg
birdbrain-verify ./pkg

The exit code is 0 on PASS and 1 on FAIL, suitable for scripting. Two utility modes:

birdbrain-verify --self-check   # print the canonical-JSON golden vector and assert the
                                # bundled core is byte-identical to the in-app core
birdbrain-verify --help

2.4 What each check proves

The verifier runs every check and collects all failures (it never stops at the first). The overall result is PASS if and only if no check is FAIL; a SKIP does not fail the package.

CheckPasses whenA FAIL means
manifest chainEvery entry recomputes to its entryHash, links via prevHash, and every v2 entry's signature validates against the bundled key.A body field was edited, a chain link broken, or a signature stripped/forged (the reason names the failing index).

capture … contentpages/{id}.mhtml exists and its SHA-256 equals the signed contentHash.The captured bytes were altered or are missing. This is the load-bearing bind of the evidence to the chain.
capture … screenshotscreenshots/{hash}.png matches the signed screenshotHash (SKIP if none recorded).The screenshot was swapped or altered.
capture … timestampThe token file's bytes equal the signed tsaToken and its message imprint equals the contentHash (SKIP if pending/none).The token was swapped, or does not bind this capture. Structural only — not TSA authenticity (see step 6).
evidence.json headThe index's recorded chain head matches the verified chain's last entry.The unsigned index was edited to point at a different head.

evidence.json artifact sweepEvery file listed in the index hashes to its recorded digest.A packaged file does not match the index (the authoritative bind is the per-capture content check above).
What a binary PASS means

Integrity + internal consistency: the signed chain is valid, every active capture's bytes bind to it, the index reconciles, and every present timestamp token binds its capture structurally. It is not a standalone authenticity claim. Proceed to the runbook's openssl ts -verify (step 6) for the canonical trusted-time proof.

3. Path B — by hand (the VERIFY.md runbook)

The package ships VERIFY.md, which is the authoritative copy of this procedure. All steps use only sha256sum, openssl, and jq. Run them from inside the unzipped package directory.

Step 1 — File integrity (index self-consistency)

Hash each artifact and compare to the index. This only proves the files match the untrusted index; the authoritative content bind is step 5.

jq -r '.artifacts[] | "\(.sha256)  \(.path)"' evidence.json | sha256sum -c -

Step 2 — Entry signature

Verify an entry's RSA signature. The signature is over the bare entryHash hex string with no trailing newline — a stray newline makes verification fail spuriously.

line=$(sed -n '1p' manifest.jsonl)                                   # pick an entry
printf %s "$(echo "$line" | jq -r '.entryHash')" > entryhash.txt    # NO newline
echo "$line" | jq -r '.signature' | base64 -d > sig.bin
openssl dgst -sha256 -verify signing-public-key.pem -signature sig.bin entryhash.txt
# => "Verified OK"

Step 3 — Recompute entryHash (canonicalization recipe)

Hashing files alone cannot detect a body-field edit that left entryHash / signature intact. Recompute the hash from the entry body: strip entryHash and signature, canonicalize, and hash.

echo "$line" | jq -cS 'del(.entryHash, .signature)' | tr -d '\n' | sha256sum
# compare the hex to:  echo "$line" | jq -r '.entryHash'

Caveats — these, not key ordering, are the real edges. Manifest keys are fixed ASCII, so jq's codepoint key sort matches Birdbrain's. What can differ is (a) string escaping of non-ASCII / control characters in values, and (b) number formatting of integers. Both jq -c and Birdbrain emit minimal integer forms and UTF-8 literals, so they agree in practice; if a hand recompute ever disagrees, look here first.

Step 4 — Chain linkage

Confirm each entry's prevHash equals the prior entry's entryHash, and index increments from 0.

jq -r '"\(.index) \(.prevHash) \(.entryHash)"' manifest.jsonl

Step 5 — Content bind (load-bearing for the evidence itself)

For each type: "capture" entry, confirm the captured bytes match the hash inside that signed entry (not the value in evidence.json). Without this you could verify a pristine signed chain yet never confirm the MHTML/PNG bytes are the ones it attests.

id=$(echo "$line" | jq -r '.captureId')
want=$(echo "$line" | jq -r '.contentHash')
got=$(sha256sum "pages/$id.mhtml" | cut -d' ' -f1)
[ "$want" = "$got" ] && echo "content OK" || echo "CONTENT MISMATCH"

# Screenshot (if the entry has screenshotHash; the file is named by that hash):
shot=$(echo "$line" | jq -r '.screenshotHash // empty')
[ -n "$shot" ] && sha256sum "screenshots/$shot.png"     # must equal $shot

Step 6 — Timestamp (canonical TSA verification)

This is the authenticity step the binary does not perform. Verify each RFC 3161 token's CMS signature against the bundled TSA chain.

openssl ts -verify -digest <contentHash> -in timestamps/<token>.tst \
  -CAfile tsa-ca-chain.pem
# => "Verification: OK"

A token whose imprint matches the content hash but whose TSA signature is invalid (a forged token) PASSES the binary's structural check and is caught only here. That is why this openssl ts -verify — not the binary — is the canonical proof of trusted time.

Why DigiCert verification works offline

The default TSA is DigiCert, whose Trusted Root G4 is present in essentially every OS trust store. openssl ts -verify succeeds against the bundled tsa-ca-chain.pem with no special configuration. If a package uses a different TSA, supply that authority's CA in -CAfile.

4. Building the verifier binary (reference)

pnpm build:verifier runs scripts/build-verifier.mjs, which:

  1. Bundles src/verifier/cli.ts and its pure dependencies (the shared verify-core, zod, @peculiar/asn1-*) into one CommonJS file with esbuild, then asserts the bundle contains no electron, src/main, better-sqlite3, keytar, or hono import — the binary must be fs+crypto only.
  2. Generates a SEA blob (node --experimental-sea-config).
  3. Injects the blob into a copy of the host node executable with postject.
  4. Re-signs per OS — macOS ad-hoc codesign (injection invalidates the host signature, which Gatekeeper would otherwise block); Windows signtool (re-sign before distribution so SmartScreen does not flag it); Linux needs no signing.

The --self-check mode exists to prove the bundling transform changed nothing: it canonicalizes a frozen golden vector and asserts the bundled core's bytes match the in-app core's, so the standalone binary and the desktop app verify by the exact same rules.

Cross-build limitation

Node SEA emits a binary for the OS it runs on; there is no cross-compilation. Build each OS's binary on that OS. (A CI release matrix that attaches per-OS binaries to releases is a deferred follow-up.)

5. Interpreting the outcome

OutcomeReading
Binary PASS + openssl ts -verify OKStrongest result: integrity intact and trusted time anchored by the external TSA. Unaltered, and provably existed by the stamped time.
Binary PASS, timestamps SKIP/pendingIntegrity intact; captures are byte-perfect but not (yet) third-party timestamped. Honest and common — not a failure.
Binary FAIL on a content/chain checkIntegrity is compromised: a captured file, hash, or chain link does not match the signed manifest. Read the named reason and failing index.
Binary PASS but openssl ts -verify failsThe structural token bind passed but the TSA signature does not validate — a forged or corrupt token. This is exactly the case the runbook catches and the binary cannot.
