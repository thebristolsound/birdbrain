Shared Case members

Seven surfaces from the members UI brief, drawn against the shipped Birdbrain UI tokens. Nothing here is implemented; the spec (docs/specs/2026-09-19-collaborative-cases-design.md) is the engineering contract. Designer calls the brief left open are settled below.

1 · Identity. The Member Code is the identifier everywhere: a mono chip with a hue dot. Hue is a scanning aid, never the only signal. The local installation is always the accent hue; the other four members take fixed hues 1–4 in join order. Five members, five hues, no collisions.
2 · Sync indicator. Top bar, right cluster, beside the extension pill, in the same pill grammar but border-only when idle. A peer dropping mid-sync demotes the pill to “2 of 3 peers” with an amber dot; it never toasts. Click opens Case settings → Members.
3 · Invite form. The copyable string is primary: invites travel over Signal or email as text. The QR sits behind a disclosure for the same-room case.
4 · Join entry. A third card on the New Case wizard start step (Blank · Import · Join a shared Case) and a ⌘K action. No new route: join runs inside the wizard.

A member is an installation. One person on two machines appears twice, with two Member Codes. Staging Pool, Selectors, to-do items, and timestamp settings stay on each machine and are not synced.

Relay

Peers connect to each other directly. When a direct connection fails, this relay carries the connection instead. The relay can see which installations connected, when, and how much data passed. It cannot read Case content: the connection is encrypted between the two peers. Case files on this disk are not encrypted by Birdbrain.
