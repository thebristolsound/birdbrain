# Testing

Paths in this document are repository-root relative.

- **Unit tests** (`tests/`) - Vitest running via Electron runtime (`ELECTRON_RUN_AS_NODE=1`). Config in `vitest.config.ts` (node environment, globals enabled). Covers database, services, store, types.
- **E2E tests** (`e2e/`) - Playwright with Electron. Config in `playwright.config.ts` (30s timeout, 1 worker, trace on-first-retry). Requires `pnpm build` first (handled by `pretest:e2e` script). New specs seed through `e2e/fixtures/seed.ts`: `createCase` drives the New Case form, and `serverToken` plus `seedCapture` post a manual capture to the local capture server the way the extension does. Older specs keep their own copies of these helpers.

**`tests/` and `e2e/` are typechecked (#337).** `pnpm typecheck` runs six projects: the three `src`/extension ones, then `tsconfig.test.node.json`, `tsconfig.test.web.json` and `e2e/tsconfig.json`. The two test projects split on **lib flavour, not on the Vitest project split**: the node one mirrors `tsconfig.node.json` (no DOM lib) and covers the tests exercising main/preload/shared/verifier; the web one mirrors `tsconfig.web.json` plus `chrome` typings and covers `tests/components`, `tests/renderer`, `tests/hooks`, `tests/lib`, `tests/extension` and every `.tsx` under `tests/`. Mixing the two libs in one project is not a shortcut — DOM's `BodyInit` rejects a `Buffer`, so a combined project invents a `TS2769` in `src/main/services/timestamp.ts` against code `tsconfig.node.json` already checks clean, and chasing it means editing production code to satisfy a lib it never runs under. That false positive is the load-bearing argument. The `Response.json()` difference (DOM returns `any`, undici returns `unknown`) is the weaker one: the node project does surface ~80 more `TS18046` errors in `tests/main/services/captureServer.test.ts`, but they are then discarded by one `Record<string, any>` helper in that file, so the split does not currently recover them.

The includes are fail-closed by construction: the node project takes everything under `tests/` and excludes the DOM directories, the web project takes every `.tsx` wherever it sits plus those directories, and each spells out `.ts`/`.mts`/`.cts` rather than `.ts` alone. A new test directory or a stray `.mts` therefore lands in a project rather than in the gap between two hand-maintained lists. `e2e/tsconfig.json` lists the same extensions plus `.tsx`. **Two gaps under `tests/` and `e2e/`.** No project sets `allowJs`, so `.js`/`.mjs`/`.cjs`/`.jsx` is compiled by nothing. And `skipLibCheck` is true in all six projects (five inherit `tsconfig.json:8`; `extension/tsconfig.json:8` sets its own), so `.d.ts` bodies sit in the program unchecked — a `tests/**/*.d.ts` shim looks gated and is not.

`eslint.config.js` still sets no `parserOptions.project`, so **linting** remains untyped — that is a separate change and a separate issue if it is wanted. `src/renderer/env.d.ts` is listed explicitly in the web test project: an ambient `.d.ts` that nothing imports is otherwise not in the program, and every `window.birdbrain` access becomes a phantom error.

A type-level assertion in `tests/` is now live, so `expectTypeOf` is available for a known-answer test rather than only a runtime probe. Note that the mutation-option objects under `src/renderer/lib/api/` are plain literals rather than React Query's `UseMutationOptions`, so their `onSuccess`/`onSettled` callbacks are typed with only the parameters they declare — a test that simulates React Query's four-argument call will not compile.

**`tests/components/**/*.test.tsx` run in the jsdom Vitest project**, not the Electron node one; the node project's `tests/**/*.test.ts` include glob does not match `.test.tsx`. A `// @vitest-environment jsdom` directive in a component test is therefore valid and may be kept for clarity — it is not an invalid override of the Electron environment.

## sharp under Electron on Linux

On some Linux systems every test file that uses sharp dies with `Worker exited unexpectedly with signal SIGSEGV`: on the maintainer's Arch machine, `thumbnails`, `export`, `exhibitModel`, `backgroundRenderer` and `burnAnnotations` under `tests/main/services/`. The missing coverage then fails the `src/main/services/*.ts` threshold. GitHub's Ubuntu 26.04 runner crashes on the same five files, and `ubuntu-latest` began resolving to it on 2026-10-27, so the workflow jobs that run the unit tests pin `runs-on: ubuntu-24.04`, which does not crash. The app is not affected: the crash needs `ELECTRON_RUN_AS_NODE=1`, which only the test runner uses.

The cause is [electron/electron#46323](https://github.com/electron/electron/issues/46323). The Electron binary links the system GLib and exposes its symbols to the whole process, while sharp's prebuilt libvips bundles its own GLib. A sharp call that releases an image, such as `sharp(buffer).metadata()`, resolves `g_object_unref` to the system copy, which then calls through a null pointer. A core dump shows it as frame 0 at address `0x0`, called from `sharp-linux-x64-<version>.node`.

The workaround builds sharp against the system libvips, so it shares Electron's GLib, and uses that build only in tests:

1. Install a libvips at least as new as sharp's `config.libvips` (8.18.7 for sharp 0.35.5), linked against the system GLib; `pkg-config --modversion vips-cpp` shows the version the build will use. If your distribution's package is older, build libvips from its release tarball into a directory of your own, with `LDFLAGS=-Wl,-rpath,<prefix>/lib` at `meson setup` so its two libraries find each other, and set `PKG_CONFIG_PATH=<prefix>/lib/pkgconfig` when you run the next step. On Arch, building libvips needs `glib2-devel`.
2. Run `pnpm build:test-sharp`. It copies sharp into `.cache/test-sharp/` (ignored) and builds it there; nothing under `node_modules` changes. Rerun it after a libvips upgrade. With `BIRDBRAIN_TEST_SYSTEM_SHARP=1` exported, `pnpm install` runs it for you, so a new worktree or a sharp upgrade needs no separate step; if that build fails, the install only warns.
3. Run tests with `BIRDBRAIN_TEST_SYSTEM_SHARP=1`, for example `BIRDBRAIN_TEST_SYSTEM_SHARP=1 pnpm test`, or export it in your shell. `tests/setup/system-sharp.ts` then hands sharp the system build in place of the prebuilt addon.

The swap is test-only by design. `src/main/services/thumbnails.ts` is a blocking-tier evidence path: its output is hashed into signed `derivation` entries that record `sharpVersion` and `libvipsVersion`, and a system build reports the same libvips version while encoding with different codec libraries. Keeping the system build out of `node_modules` keeps it out of the dev app and every package. The cost is that thumbnail bytes in local tests may differ from CI; CI stays the authority for them.

Two approaches that look simpler do not work. Preloading the prebuilt `libvips-cpp.so` with `LD_PRELOAD` crashes Electron itself, and loading the addon with `RTLD_DEEPBIND` aborts in `free()` because Electron's allocator and the deep-bound library disagree.

## Test reliability probe

Diff coverage shows that a changed line ran under a test. It does not show that any assertion depends on that line. `pnpm test:reliability` checks the second question for the unit tests, and `.github/workflows/test-reliability.yml` runs it on every pull request that changes `src/`, `extension/src/` or `tests/`. The job is advisory: it writes its report to the job summary and as warning annotations on the diff, exits 0 when it has findings, and fails only when the probe cannot run. It is not a required check, and the dispatch CI read (`.github/scripts/dispatch/checks.sh`) lists it as ignored, so a failed or running probe job neither holds the automated review nor sends the pull request to a fix round.

The probe runs two experiments against the merge base with `origin/main` (`--base <ref>` for another):

- **Revert probe.** It restores every changed TypeScript source file under `src/` and `extension/src/` to its merge-base content, except the files the unit runner never loads (listed in `scripts/test-reliability/lib/changes.mjs`), keeps the branch's tests, and reruns the test files the branch added or edited. A test the branch added or edited that still passes did not need the change. For a fix or a feature, that test does not pin the change. For a refactor that should preserve behaviour, it is the expected result.
- **Mutation probe.** For each changed source file it runs `vitest related` once as a baseline, then makes one change at a time on the lines the branch added: it flips a comparison, logical or arithmetic operator, swaps `true` and `false`, drops a `!`, negates an `if` condition, returns `undefined` in place of a value, or deletes a call statement. Each mutant reruns the baseline's test files with `--bail=1`. A mutant that leaves every test green has survived, and the line it changed is one no assertion depends on. A file whose baseline is red is not probed, and a file no unit test imports is listed as such.

A surviving mutant is not always a gap. An equivalent mutant changes nothing any input can observe, for example `>=` in place of `>` where the two values can never be equal. Read each survivor and name the input that would expose it, or the reason none exists.

The probe samples at most 40 mutants (`--max-mutants`), spread evenly over the changed lines. Both experiments share one time budget, 15 minutes by default (`--budget <seconds>`): each test run is stopped when the budget runs out, and the report counts a mutant it stopped as not run for time. `--no-revert` and `--no-mutate` turn off one experiment, `--json` prints the result as JSON, `--summary <file>` appends the Markdown report to a file, and `--annotations` prints workflow annotations.

The probe does not run end-to-end specs, because each mutant would need a fresh `pnpm build`. The `test-reliability-reviewer` agent (`.claude/agents/test-reliability-reviewer.md`) reads changed specs and unit tests against their titles, and uses the probe's report as evidence.

Both experiments edit tracked files while the tests run and put them back afterwards. The probe refuses to start on a tree with uncommitted changes, and `SIGINT` or `SIGTERM` stops the running tests and restores the files before it exits. While any file is edited, `.cache/test-reliability/journal.json` lists it. A run killed with no chance to restore leaves the journal, and the next run refuses to start and prints the `git checkout` command that restores the files. Do not edit files or run other tests in the same tree while the probe runs.
