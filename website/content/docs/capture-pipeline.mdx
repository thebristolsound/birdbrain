## 1. Overview

The capture pipeline is the core data ingestion path in Birdbrain. The Chrome extension collects
a page as MHTML plus a screenshot, extracted text, and response headers, and posts it over HTTP
to a Hono server bound to `127.0.0.1:19845` inside the Electron main process. The Capture
Lifecycle then hashes the content while streaming it to disk, appends a signed entry to the
per-case manifest, records the capture in SQLite, schedules post-capture work, and pushes
real-time events to the renderer.

MHTML is the only format the extension produces. Captures with `format: 'html'` exist only as
read-only legacy rows from before the MHTML migration; they have no manifest entry and no ingest
path.

**Current build status.** The wire protocol defines three capture sources (`auto`, `manual`,
`selector`), and the server validates all three. In the shipped extension, session auto-capture
and selector-triggered auto-capture are disabled by a hotfix in `extension/src/background.ts`
(the code paths exist but are commented out); the README states the same limitation. Manual
capture — the popup capture button and the right-click context menu — is the live extension
path. The desktop app's background recapture is a separate acquisition path that renders a URL
in a hidden window and feeds the same lifecycle ingest.

## 2. Capture sources

### Manual capture

Manual capture is the extension's live path. Triggers:

- The capture button in the extension popup (`MANUAL_CAPTURE` message to the background worker).
- The right-click menu: **Birdbrain -> Capture Full Page** and **Capture Full Page (Scrolling)**.

Behavior:

- Requires an explicit `caseId`; the server validates that the case exists and is not archived.
- The background worker re-reads the tab's URL at capture time (the tab may have navigated since
  the popup rendered) and refuses to start until the ignore rules have loaded from the server —
  with no rules it cannot know whether the operator excluded the page.
- An in-flight guard keyed by tab and case prevents double submission.
- A toast on the page reports the outcome: success, degraded (screenshot dropped), or error.

### Auto and selector capture (disabled)

When enabled, auto capture fires on page-load completion during an active session (case inferred
from the server's active case), and selector capture fires when page text matches a case's
Selectors, in `auto` or `notify` mode. Both paths are currently commented out in the background
worker. Selector *matching* still runs: matches highlight on the page, update the toolbar badge,
and are reported in the popup — they just do not trigger captures.

The server-side validation for all three sources remains live, so re-enabling the paths is an
extension-side change.

### Recapture

Recapture is app-initiated: a fresh background capture of an existing capture's URL, rendered in
a hidden window and stored as a linked sibling that supersedes the original (`method:
'background'`, `supersedesCaptureId`). It reuses the same lifecycle ingest described below and is
otherwise out of scope for this page.

## 3. The capture endpoint

### `POST /api/captures`

One multipart/form-data endpoint for all sources, validated by `CaptureUploadSchema`
(`src/shared/schemas.ts`). Principal fields:

| Field | Notes |
|-------|-------|
| `source` | `auto`, `manual`, or `selector` — the wire union; `recapture` never arrives here |
| `caseId` | Required for `manual` and `selector`; inferred from the active case for `auto` |
| `url`, `title`, `timestamp` | Page identity as the extension observed it |
| `mhtml` | The MHTML file part — required |
| `screenshot` | Optional PNG file part |
| `textContent` | `document.body.innerText` at capture time |
| `headers` | Main-frame response headers, when the cached set still matches the URL |
| `browserVersion`, `userAgent`, `extensionVersion`, `httpStatus` | Provenance fields |

### Middleware stack, in order

1. **Host-header guard.** Any request whose `Host` is not a loopback literal is rejected before
   the body is read — the DNS-rebinding defense.
2. **Body limit.** 250 MB across the request.
3. **CORS.** Only `chrome-extension://` and localhost origins are granted.
4. **Token auth.** Every POST requires `X-Birdbrain-Token`, the per-installation secret. GET
   endpoints are unauthenticated by design and disclosed as such in SECURITY.md.

### Validation order inside the handler

1. **Operator-name gate.** If no operator name is configured in Settings, the capture is refused
   (400) and a `failed` event is emitted. Nothing is stored without an attributable operator.
2. **Case resolution.** For `auto`: an active session and active case must exist. For `manual`
   and `selector`: the named case must exist and not be archived. Case resolution runs *before*
   the exclusion check because exclusions are per-case — the case's policy cannot be known until
   the case is.
3. **Exclusion check.** The URL is matched against the case's effective ignored-URL patterns
   (global list plus the case's exclusions, or the case's alone in `override` mode). A match
   answers 403 naming the pattern and emits a `skipped` event.
4. **Manual dedup.** A manual capture of the same case and URL within the dedup window (5
   seconds, `MANUAL_DEDUPE_WINDOW_MS`) answers 409 and emits a `skipped` event.
5. **Screenshot size policy.** A screenshot part over 100 MB (`MAX_SCREENSHOT_SIZE`) is dropped
   rather than failing the capture; the response and the `stored` event carry the warning, and
   the extension shows a degraded toast. A silently missing artifact would let a clean-looking
   capture lose one.
6. **Ingest.** The MHTML stream is handed to the Capture Lifecycle (section 5).

### Response

```typescript
{
  captureId: string
  hash: string             // SHA-256 of the stored MHTML bytes
  manifestIndex: number
  status: 'ok'
  source: string
  screenshotStatus: 'saved' | 'dropped' | 'none'
  screenshotWarning?: string
}
```

On any ingest exception the server logs, emits a `failed` event, and answers 500.

## 4. What the extension collects

Inside the suppression boundary (below), a manual capture collects in parallel:

- **MHTML** via `chrome.pageCapture.saveAsMHTML` — the browser-rendered page with its
  subresources in one file.
- **Tab metadata** (title) via `chrome.tabs.get`.
- **Plain text** — `document.body.innerText`, executed in the page via `chrome.scripting`.
- **A screenshot**, when the `captureScreenshots` setting allows: the full-page path stitches
  viewport slices on an `OffscreenCanvas` in the content script; the scrolling variant first
  scrolls to trigger lazy-loaded content (with a 120-second budget); each falls back to the next
  simpler path, ending at a single viewport shot. A hard byte budget bounds the bitmap.

**Response headers** are cached per tab from `chrome.webRequest.onHeadersReceived` (main frame
only) and attached only when the cached URL still matches the captured URL — no headers rather
than the wrong page's headers. The cache is cleared on navigation start and tab close.

### Capture-UI suppression

Birdbrain injects UI into the page it captures: the progress toast (`extension/src/toast.ts`) and
selector highlights (`extension/src/content.ts`). Both would otherwise be rendered into
screenshot frames and serialised into the archived MHTML, putting tool chrome inside evidence.

The suppression protocol (`extension/src/captureSuppression.ts`) is one suppress/restore boundary
around every capture:

- Each piece of in-page UI registers a teardown (`registerCaptureUiTeardown`). One
  `suppressCaptureUi()` call removes all of it; new in-page UI registers there rather than being
  added to each capture path. It must also be added to `removeInjectedBirdbrainUi()`
  (`extension/src/captureHygiene.ts`), the background's fallback strip for a tab whose content
  script is orphaned or cannot clear itself: that function is serialised into the page by
  `chrome.scripting.executeScript` and cannot reach the registry, so the two lists are kept in
  step by hand.
- The background wraps a capture in `withSuppression()`: it strips the UI before any frame or DOM
  snapshot is taken, refuses to inject UI into the tab while any capture on it is still
  collecting frames, holding toasts for delivery once the tab is idle rather than dropping them,
  and restores the highlights when the capture settles, including when it fails, so a failed
  capture never leaves the page stripped.
- Every screenshot path re-runs suppression immediately before each frame it takes: viewport,
  full-page, scrolling, and the fallbacks between them. The full-page path re-suppresses before
  every viewport slice, not once per capture.
- A path that cannot clear the page aborts the whole capture rather than the screenshot alone.
  The MHTML is collected inside the same bracket and is a snapshot of that same uncleaned page,
  so storing it as an ordinary screenshot-less capture would keep evidence that cannot be shown
  clean while telling the operator nothing.

What this establishes and what it does not: a screenshot produced by these paths is of a page
from which Birdbrain's own injected nodes had been removed immediately before each frame was
taken. The archived MHTML carries a slightly weaker claim of the same kind. It is a snapshot of a
page that was stripped when the capture bracket opened, and into which Birdbrain injected nothing
while the capture was collecting; there is no strip at the instant `pageCapture.saveAsMHTML`
serialises, because that API gives the extension no such hook. Neither is a statement about page
content the site itself renders, about anything injected by other extensions, or about the page's
state before or after the capture window.

### Toast feedback

| Status | Message | Notes |
|--------|---------|-------|
| `capturing` | "Capturing page..." | Shown once frames are collected; held while any capture on the tab is still collecting |
| `success` | "Page captured" | |
| `degraded` | "Captured (screenshot too large)" | The capture stored; the oversized screenshot was dropped |
| `error` | Mapped from the failure | 400 -> "Capture rejected: (detail)", 403 -> "URL is blacklisted", 404 -> "Case not found", 500 -> "Server error - check Birdbrain app", network -> "Can't reach Birdbrain - is it running?", suppression failure -> "Capture aborted: Birdbrain UI could not be removed from the page" |

Outcome toasts are held, not dropped, while another capture on the tab is collecting frames — how
a capture ended is the operator's only signal that it succeeded.

## 5. Ingest: the Capture Lifecycle

`ingestMhtmlCapture` (`src/main/services/captureLifecycle.ts`) is the forensic-bearing path.

1. **Stream-write and hash.** `writeMhtmlStream` (Capture Store) writes the MHTML to disk in a
   single pass while feeding a SHA-256 hasher, enforcing the 200 MB cap (`MAX_MHTML_SIZE`) and
   unlinking partial files on overflow or error. The hash covers exactly the bytes on disk.
2. **Content-address the sidecars.** The screenshot and extracted-text digests are computed
   *before* the manifest entry is appended, so the same hex binds the signed manifest body and
   the database mirror. Absent artifacts are omitted (`undefined`, never `null` or empty) so
   legacy entry bodies stay byte-stable.
3. **Anchor the headers.** Captured response headers are embedded in the signed entry when
   present.
4. **TLS corroboration re-fetch.** For HTTPS URLs, the main process re-connects to the origin
   after storage and records the certificate chain served *at that moment*. This is corroboration
   only — it binds nothing about the captured transaction (ADR-0002) — and it is fail-soft: a
   re-fetch problem can never fail the capture.
5. **The write-ahead manifest seam.** `withCaptureEntry` appends the signed entry, then runs the
   side effects — write the `.txt` and `.png` sidecars, insert the database row. Any failure
   re-throws: the seam truncates the manifest back to its pre-append offset and the store deletes
   the written artifacts. The manifest never records a capture that did not land.
6. **The database row** duplicates the chain-linkage fields (`manifestIndex`, `prevHash`,
   `entryHash`) so the database and manifest can be cross-checked against each other during
   verification.

After ingest returns, two things happen off the request path:

- The capture id is handed to the **RFC 3161 timestamp worker** without blocking; the capture's
  trusted time stays `pending` until a token lands.
- `setImmediate` schedules **post-capture work**: selector matching
  (`selectorLifecycle.runActiveSelectorsForCapture`) against the extracted text, then **data
  extraction** into `extracted_data` (the indicator categories behind the Data Explorer).
  Extraction runs synchronously on the main process and is timed as a slow operation for
  Settings -> Diagnostics; a failure in either task is logged and never fails the capture.

### Storage layout

```
{storageRoot}/
  {caseId}/
    manifest.jsonl            -- signed, hash-chained audit log (one per case)
    {captureId}.mhtml         -- the captured page
    {captureId}.png           -- screenshot (when taken)
    {captureId}.txt           -- extracted plain text (when present)
    {captureId}_thumb.jpg     -- derived thumbnail
```

The database stores relative paths; the Capture Store (`captureStore.ts`) owns the layout, and
everything — ingest, verify, delete, extraction, thumbnailing, orphan scanning — goes through it.

## 6. Verification

`verifyCapture` re-establishes a capture's standing from primary material:

1. Stream the MHTML from disk and recompute SHA-256.
2. Verify the whole manifest chain for the case.
3. **Anchoring check.** A valid chain can still be truncated — removing trailing entries leaves a
   shorter, internally valid chain — so verification confirms this capture's content hash is
   anchored at its recorded manifest index before trusting the stored-hash comparison.
4. **Sidecar binding.** Screenshot and text digests are recomputed against the hashes recorded in
   the *signed manifest entry*, never against the database mirror, which is a cache an attacker
   could edit alongside the file.
5. Status is one of `verified`, `tampered`, `missing`, `chain-broken`, or `legacy` (pre-MHTML
   rows, which have no manifest entry and are grandfathered rather than judged).

Trusted time is resolved separately and attached to every result: `rfc3161`, `pending`, or
`none`. It is orthogonal to integrity — a byte-perfect capture is integrity-verified whether or
not a timestamp token exists. The result is persisted so the UI shows the *last* verification
run; the displayed state is not a live check, and **Re-verify** produces a current one.

## 7. Deletion

### Deletion is not redaction

Each case directory carries a hash-chained, append-only manifest (`manifest.jsonl`). Deleting a
capture removes its database row and its files, and appends a `deletion` entry recording the
capture id, the time, the content hash and the operator. It does **not** remove the original
`capture` entry. That is what append-only means, and it is what lets a reader confirm the chain
was never rewritten.

The consequence is that **the deleted capture's URL survives deletion**, along with its capture
time and hashes, because those fields live on the `capture` entry rather than the `deletion` one.
Any export that includes the audit trail (the default) ships that manifest, so a URL captured in
error is still in the evidence package handed to a third party.

Deletion is therefore a storage operation, not a redaction mechanism. A case is contaminated by
everything ever captured into it, and the remedy for a sensitive URL is a new case rather than a
delete. Redaction proper, a URL commitment scheme that lets an entry be verified without
disclosing what it points at, is tracked separately.

Deletion is write-ahead like ingest: the signed `deletion` entry is appended first, then files
are unlinked and the row removed, with the manifest rolled back if the side effects fail. Deletes
within one case are serialised through a per-case queue, because a rollback is a truncation and
two interleaved deletes could truncate each other's entries. Batch deletion commits a prefix: one
ordinary entry per capture, in order, halting at the first failure. Non-operator deletions (the
pipeline self-test's cleanup) record a `reason` on the entry so a chain reader can tell them from
an operator deleting evidence.

### Unreconciled deletions

The write-ahead ordering leaves a narrow window: if the app is killed between the manifest flush
and the row delete, the manifest holds a valid deletion entry while `captures` still holds the
row. Nothing about the chain is wrong in that state, so chain verification reports it as valid —
which is why **Settings -> Diagnostics -> Unreconciled deletions** exists. It re-verifies the
chain of every case it can read and joins the deletion entries against live capture rows, listing
any entry the database has not caught up with. Cases it could not read are named separately, and
nothing is claimed about them. Archived cases are not scanned at all.

What a finding establishes is bounded, and the panel says so: the chain verifies, and the row is
still present. Whether the capture's files are still on disk is **not** part of the claim — the
check never reads them.

There is no automatic repair, because the manifest holds the claim rather than the data:
truncating the entry would be a lie if the files are in fact already gone. The recovery action is
to **delete the capture again from its case**. That appends a fresh signed deletion entry and
removes the row; it succeeds whether or not the files survived, because each unlink is guarded by
an existence check. The stale entry stays in the chain, as append-only requires.

An evidence package exported from an unreconciled case already fails verification:
`evidence.json` lists a capture the signed manifest records as deleted, which the standalone
verifier reports as an `evidence.json coverage` failure naming the capture and saying the chain
records it as deleted.

The verifier stops there and does not call it an interrupted delete, because it cannot tell one
from the other. An `evidence.json` edited to re-add a capture that was legitimately deleted
produces the same failure on the same branch, and naming a crash would hand that edit an innocent
explanation.

## 8. URL filtering

Both sides consult the same pattern grammar (`src/shared/urlPatterns.ts`): regex literals in
`/slashes/`, globs with `*`/`?`, and plain substrings.

- **The server enforces.** The effective list for a case is the operator's global
  `ignoredUrlPatterns` combined with the case's own exclusions, or the case's alone in
  `override` mode (`exclusionPolicy.ts`). Operator-supplied regexes are evaluated inside a
  `node:vm` sandbox with a 200 ms budget, so a pathological pattern fails closed as a no-match
  instead of stalling the app. The exclusion list blocks every capture route into a case,
  manual included.
- **The extension pre-filters.** It mirrors the effective list from the status poll and skips
  blocked URLs client-side — advisory only; the server remains the enforcement point. Until the
  first successful poll loads the rules, manual capture refuses to start rather than guessing.
- **A hardcoded default list** in the extension skips browser-internal schemes (`chrome://`,
  `about:`, `data:`, `file:`, and the capture server itself) before anything is sent.

The pipeline self-test route is the one producer the exclusion list deliberately does not cover:
its URL is a fixed sentinel and its body a literal, so no operator-supplied content enters the
case, and a broad pattern like `/./` must not be able to break the operator's only proof that the
pipeline works.

## 9. Observability

### Capture events

```typescript
interface CaptureEvent {
  type: 'received' | 'stored' | 'failed' | 'skipped'
  captureId?: string
  source: CaptureSource
  url: string
  timestamp: string
  error?: string             // 'failed'
  skipReason?: string        // 'skipped'
  durationMs?: number        // 'stored'
  screenshotWarning?: string // 'stored' with a dropped screenshot
}
```

| Event | Emitted when |
|-------|--------------|
| `received` | The request passed validation and ingest is starting |
| `stored` | The lifecycle completed: manifest entry, files, and row all landed |
| `failed` | Any exception in the pipeline, or the operator-name gate refused |
| `skipped` | An exclusion pattern matched, or manual dedup caught a duplicate |

Events flow over the `CAPTURE_ACTIVITY` IPC channel through the preload bridge into the Zustand
store, which keeps a ring buffer of the 50 most recent events (aggregate success/fail/skip
counters accumulate independently). The `CaptureHealth` component in the top bar renders the
counters, connection and session state, the last error, the activity list, and the two self-test
buttons. A separate `NEW_CAPTURE` event carries the full capture row so the renderer prepends it
to the list without a refetch.

### Self-tests

- **Test Pipeline** (`POST /api/captures/test`): ingests a fixed literal body under the sentinel
  URL `birdbrain://pipeline-test` through the real lifecycle — manifest entry, files, row — then
  deletes it through the lifecycle, appending a matching `deletion` entry with reason
  `pipeline-test`. The residue is bounded and honest: on the happy path the chain gains a
  capture/deletion pair; cleanup is best-effort, so a matched pair is the normal case, not a
  guarantee.
- **Test HTTP** (`captures:testHttp` IPC): a `fetch` of `GET /api/status` from the main process,
  proving the listener independently of the extension.

## 10. Connection management

- The extension polls `GET /api/status` on a `chrome.alarms` schedule of 30 seconds — the MV3
  minimum for a repeating alarm — plus once at worker startup, and immediately after the popup
  switches the active case (so highlights and cached counts never lag a case switch by a poll
  interval).
- The server counts a poll from an extension origin as a heartbeat and reports the extension
  connected or disconnected to the renderer as that heartbeat appears and lapses.
- The status response carries what the extension mirrors: active case, session state, capture
  count, the effective ignored-URL patterns, and the screenshot toggle. The per-installation
  token is included only for extension and origin-less callers, never for web origins.

### Badge states

| State | Badge |
|-------|-------|
| Disconnected | `!` on gray |
| Connected, idle | empty |
| Session active | capture count on red |
| Selector matches on page | match count on blue |

## 11. Extension attach routes

Three further POST routes serve the extension's annotate-from-the-browser features. All follow
the same active-case discipline as selector creation: the request's `caseId` must match the
server's active case.

- `POST /api/captures/lookup` — whether the case already holds a capture of a URL (canonicalized
  comparison). A read carried as a POST on purpose: the token guard fires on POST only, and a GET
  would answer any local process without a token.
- `POST /api/tags/apply` and `POST /api/notes` — apply a tag or create a note against the capture
  of a URL, *auto-capturing first* when the case holds none (the request carries an MHTML payload
  for that path). The resolve-or-ingest step is serialised per case and URL so two concurrent
  attaches cannot each observe "no capture" and ingest duplicates. The attach runs strictly after
  a successful resolve, so a failed ingest attaches nothing.

## 12. Design decisions

### One endpoint, discriminated by source

An earlier design had three near-identical capture endpoints duplicating most of their logic. The
unified endpoint keeps the shared pipeline (hash, storage, manifest, events) in one place, makes
the per-source validation rules one explicit decision tree, and cannot drift between sources.

### Dedup on both sides, for different reasons

The server enforces a short manual-capture dedup window (5 seconds per case and URL, answering
409) because double-clicks and repeated context-menu hits are operator slips the server should
absorb. The disabled auto-capture path carries its own client-side dedup map so that, when
enabled, the extension avoids the HTTP round trip entirely for recently captured URLs.

### Fire-and-forget post-capture work

Selector matching and data extraction run via `setImmediate` after the response is sent: the
extension should not wait on them, and a failure in either must not make a stored capture look
failed. Each task is independently guarded and logged.

### A ring buffer for activity

The renderer keeps the 50 most recent capture events — enough recent history to debug a session
without unbounded growth — while aggregate counters accumulate independently, so rotation never
under-reports totals.
