# Forensic MHTML Capture — Design Spec

**Date:** 2026-04-05
**Author:** Matt Donovan
**Status:** Approved, pending implementation plan

---

## 1. Problem

Birdbrain currently captures pages as flat HTML via the `freeze-dry` library inside the Chrome extension's content script. This produces a single HTML string with inlined resources, but the result is:

- Not self-contained in the forensic sense — subtle resource loss is possible and hard to audit.
- Not a recognized court format — freeze-dry is not a Chromium-native mechanism.
- Missing a formal chain-of-custody audit trail — we store a SHA-256 hash, but nothing binds capture N to capture N-1 or records operator identity, tool versioning, or deletion history.

We need captures that:

1. Open as exact replicas of the original page offline, with no internet connection required.
2. Carry forensic metadata sufficient to support authentication under US FRE 901(b)(9) and UK ACPO Principle 3.
3. Produce a tamper-evident audit log per case so an independent examiner can verify the chain of custody end-to-end.

## 2. Approach

Replace flat-HTML capture with **MHTML generated by Chromium's native `chrome.pageCapture.saveAsMHTML()` API**, wrapped in a forensic pipeline that includes:

- SHA-256 content hashing (streaming, on write)
- Per-case append-only hash-chained manifest (`manifest.jsonl`)
- Operator identity (stable installation UUID + optional investigator name) stamped on every entry
- Deletion audit events in the same chain
- UI integrity-verification affordances (per-capture and per-case)
- Electron `<webview>` rendering of MHTML with JavaScript disabled

Legacy flat-HTML captures already in users' databases are left untouched — the viewer handles both formats based on a new `format` column. Only new captures use MHTML.

This approach matches the forensic stance taken by Hunchly, Pagefreezer, and FAW, and is grounded in the research summarized in §14 below.

## 3. Architecture & Data Flow

```
┌─────────────────────────┐
│ Chrome Extension (bg)   │
│  chrome.pageCapture     │  ← Blink-native MHTML serialization
│  .saveAsMHTML({tabId})  │
└───────────┬─────────────┘
            │ Blob + metadata
            │ multipart/form-data POST
            ▼
┌─────────────────────────┐
│  Hono capture server    │
│  POST /api/captures     │
│   1. Validate           │
│   2. Stream-write .mhtml│  ← single pass write+hash, memory-safe
│   3. SHA-256(raw bytes) │
│   4. Append to manifest │  ← caseId/manifest.jsonl (hash-chained)
│   5. Insert DB row      │  ← write-ahead paired w/ (4)
│   6. Emit new-capture   │
└───────────┬─────────────┘
            │ IPC event
            ▼
┌─────────────────────────┐
│  Renderer               │
│  CaptureViewer          │
│  <webview src=file://…  │  ← JS disabled, sandboxed
│         .mhtml"/>       │
└─────────────────────────┘
```

**Single-producer contract:** new captures go only through `chrome.pageCapture.saveAsMHTML()`. No fallback to freeze-dry. If the API fails for a given tab, capture surfaces a clear error and nothing is stored.

**Screenshots stay.** PNG screenshot is still captured in parallel via `chrome.tabs.captureVisibleTab()`. Used for the thumbnail strip and the "Screenshot" tab.

**Text for FTS stays.** Content script still extracts `document.body.innerText` and posts alongside the MHTML, keeping FTS indexing simple (no server-side MHTML parsing).

## 4. Chrome Extension Changes

**Manifest (`extension/manifest.json`):** add `"pageCapture"` to permissions.

**Background (`extension/src/background.ts`):** new capture flow:

```
1. (parallel) start chrome.tabs.captureVisibleTab()   → PNG bytes
2. (parallel) content script EXTRACT_TEXT             → innerText + title
3. chrome.pageCapture.saveAsMHTML({ tabId })          → Blob (MHTML)
4. fetch http://127.0.0.1:19845/api/captures
      method: POST
      body: FormData
        - mhtml:      File (the MHTML blob)
        - screenshot: Blob (PNG)  [optional]
        - metadata:   JSON string (source, caseId, url, title, timestamp,
                                    textContent, userAgent, matchedSelectors,
                                    extensionVersion, browserVersion, httpStatus,
                                    headers)
```

**Content script (`extension/src/content.ts`):** stripped down. `freeze-dry` dependency removed from `package.json`. Content script's only job is text/title extraction + selector matching. The `EXTRACT_PAGE` message becomes `EXTRACT_TEXT`.

**Error surfacing:** when `saveAsMHTML` throws (privileged URLs, tab closed mid-capture, unsupported view type), background posts the failure to a new `POST /api/captures/errors` endpoint. No silent drops.

**HTTP headers:** extension already captures response headers via `chrome.webRequest` listeners; these continue to be included in metadata and stored in `captures.headers`.

## 5. Capture Server Changes

**`POST /api/captures` — multipart.** Hono's `c.req.parseBody()` handles `multipart/form-data` natively. Metadata JSON is validated against a typed shape in `src/shared/ipc.ts` before touching disk.

```
POST /api/captures   Content-Type: multipart/form-data
  mhtml      — required, the .mhtml file
  screenshot — optional, PNG
  metadata   — required, JSON-stringified object
```

**Processing pipeline:**

1. Parse multipart → validate metadata JSON shape.
2. URL blacklist check (unchanged).
3. Source-specific validation (unchanged: auto/manual/selector rules).
4. Dedup check (unchanged windows, still manual-only).
5. Compute SHA-256 over the raw MHTML file bytes during streaming write (not a string — stream + `createHash('sha256').update(chunk)`).
6. `saveCaptureStreaming()` writes `caseId/<captureId>.mhtml` + optional `.png` + `.txt`.
7. Append manifest entry (§7) via the write-ahead pattern so manifest and DB cannot drift (see §7.5).
8. `db.insertCapture()` with new forensic columns populated — rolls back the manifest append on failure.
9. Schedule post-capture selector matching (unchanged).
10. Emit `NEW_CAPTURE` event (unchanged).
11. Return `{ captureId, hash, manifestIndex, status: 'ok', source }`.

**Hash service (`src/main/services/hash.ts`):** gains `hashBuffer(buf: Buffer): string`. Existing `hashContent(str)` stays for manifest signing.

**New endpoint `POST /api/captures/errors`** — accepts `{ source, caseId, url, reason, timestamp, metadata }` from the extension. Emits `CAPTURE_ACTIVITY` with `status: 'failed'`.

**Request size limits:** Hono body parser limit raised to ~200MB with a hard cap enforced during streaming write (§6). Cap is configurable via a `maxCaptureSizeBytes` setting, 200MB default.

## 6. Storage Layer

**File layout:**

```
<storageRoot>/
  <caseId>/
    <captureId>.mhtml        ← new (was .html)
    <captureId>.png          ← unchanged
    <captureId>.txt          ← unchanged (from innerText)
    <captureId>_thumb.jpg    ← unchanged (generated on-demand from .png)
    manifest.jsonl           ← NEW — per-case hash-chained audit log
```

**Streaming write + hash (memory-conscious):** MHTML uploads are streamed, never materialized whole in a JS string.

```ts
// pseudo
const mhtmlFile = body.mhtml as File
const writeStream = fs.createWriteStream(destPath)
const hasher = createHash('sha256')

for await (const chunk of mhtmlFile.stream()) {
  hasher.update(chunk)
  writeStream.write(chunk)
}
writeStream.end()
await finished(writeStream)
const hash = hasher.digest('hex')
const bytes = writeStream.bytesWritten
```

**Size enforcement:**
- Soft warning logged at 50MB.
- Hard cap at 200MB — abort mid-stream, delete partial file, return `413 Payload Too Large` with reason code surfaced in Capture Activity.

**New storage API:**

```ts
saveCaptureStreaming(
  caseId: string,
  captureId: string,
  mhtmlStream: ReadableStream,
  screenshot?: Blob,
  textContent?: string,
  maxBytes?: number
): Promise<{ mhtmlPath, screenshotPath?, textPath?, hash, bytes }>
```

Old `saveCapture(..., html: string, ...)` signature is removed.

**Reading captures for the viewer:** viewer loads via `file://` URL (§9), so main process doesn't buffer MHTML at render time. `CAPTURES_GET_CONTENT` for `type: 'html'|'mhtml'` returns a `file://` path string instead of file contents.

## 7. Forensic Manifest (Hash-Chained JSONL)

**Purpose:** portable, tamper-evident audit log for a case. Plain `.jsonl` file, one JSON object per line, exports cleanly, verifiable by any third party with `sha256sum` + `jq`.

**Location:** `<storageRoot>/<caseId>/manifest.jsonl` — append-only.

### 7.1 Entry shape (capture event)

```json
{
  "type": "capture",
  "index": 42,
  "captureId": "7d3f…",
  "timestamp": "2026-04-05T14:23:51.742Z",
  "url": "https://example.com/article",
  "title": "Article Title",
  "format": "mhtml",
  "contentHash": "a7b2c…",
  "sizeBytes": 2847319,
  "httpStatus": 200,
  "source": "manual",
  "userAgent": "Mozilla/5.0 …",
  "browserVersion": "Chrome/131.0.6778.86",
  "toolVersion": "birdbrain@0.x.y",
  "extensionVersion": "0.x.y",
  "operatorId": "inst-9f2e…",
  "operatorName": "Matt Donovan",
  "prevHash": "b5e1…",
  "entryHash": "c9f4…"
}
```

### 7.2 Entry shape (deletion event)

```json
{
  "type": "deletion",
  "index": 43,
  "timestamp": "2026-04-07T09:15:22.301Z",
  "targetCaptureId": "7d3f…",
  "targetCaptureIndex": 42,
  "targetContentHash": "a7b2c…",
  "targetUrl": "https://example.com/article",
  "reason": "duplicate capture",
  "operatorId": "inst-9f2e…",
  "operatorName": "Matt Donovan",
  "toolVersion": "birdbrain@0.x.y",
  "prevHash": "c9f4…",
  "entryHash": "e1a8…"
}
```

### 7.3 Chain semantics

- `entryHash = SHA-256(canonicalJSON(entry minus entryHash))`. Canonical JSON: keys alphabetical, no whitespace.
- `prevHash` of entry N equals `entryHash` of entry N−1.
- First entry has `prevHash: null`.
- Tampering with any past entry breaks the chain at that point and all subsequent `prevHash`/`entryHash` pairs become invalid.

### 7.4 Deletion semantics

- User deletes a capture → `.mhtml`, `.png`, `.txt`, `_thumb.jpg` files removed.
- DB row removed (current `CAPTURES_DELETE` handler behavior).
- `deletion` entry appended to `manifest.jsonl` **before** files and DB row are touched, via the write-ahead pattern (§7.5) so chain and DB stay aligned.
- Chain preserves: what existed, its content hash, who deleted it, when — forever.
- Delete confirm dialog gains an optional "Reason" text field and a note: *"Deletion will be recorded in the case's audit log."*

### 7.5 Append write pattern

`better-sqlite3` transactions are synchronous, so we use a **write-ahead manifest** pattern rather than nesting file I/O inside the DB transaction:

```ts
// 1. Record manifest file length before append (rollback anchor)
const anchorBytes = statSync(manifestPath).size

// 2. Append entry with sync fs calls (fsync before DB commit)
const entryJson = canonicalStringify(entry) + '\n'
const fd = openSync(manifestPath, 'a')
try {
  writeSync(fd, entryJson)
  fsyncSync(fd)
} finally {
  closeSync(fd)
}

// 3. Insert DB row in sync transaction; if it throws, truncate the manifest
//    back to anchorBytes as compensation.
try {
  db.transaction(() => db.insertCapture({ ...captureFields, manifestIndex, entryHash, prevHash }))()
} catch (err) {
  truncateSync(manifestPath, anchorBytes)   // rollback the append
  throw err
}
```

**Invariant:** either both the manifest entry and the DB row exist, or neither does. If the process crashes between step 2 and step 3, the next startup verifies manifest tail against DB `manifest_index` and truncates dangling manifest entries (surfaced as an audit log warning).

Deletion events follow the same pattern: append deletion entry → sync DB delete → compensate by truncating if DB delete fails. Because the deletion event records `targetContentHash` independently, it doesn't matter that the capture row is gone after commit.

### 7.6 Concurrency

Per-case async mutex (`Map<caseId, Promise>`) serializes capture and deletion appends. Different cases run concurrently.

### 7.7 New service: `src/main/services/manifest.ts`

```ts
appendCaptureEntry(caseId, entry): Promise<{ index, entryHash, prevHash }>
appendDeletionEntry(caseId, deletion): Promise<{ index, entryHash }>
verifyManifest(caseId): Promise<{
  valid, brokenAt?, expectedHash?, actualHash?,
  totalEntries, captureCount, deletionCount,
  firstEntry?: string, lastEntry?: string
}>
readManifest(caseId): AsyncIterable<CaptureManifestEntry>
```

### 7.8 Export integration

`export` service includes `manifest.jsonl` + a `VERIFICATION.md` file with shell-command instructions for offline chain verification (using `sha256sum`, `jq`, and a short inline script).

## 9. Viewer Changes

**Page tab switches from `<iframe srcDoc>` to Electron `<webview>` for MHTML.**

```tsx
// Legacy path (format === 'html')
<iframe sandbox="allow-same-origin" srcDoc={htmlContent} />

// New path (format === 'mhtml')
<webview
  src={fileUrl}
  webpreferences="javascript=no, sandbox=yes, contextIsolation=yes, nodeIntegration=no"
  disablewebsecurity="false"
  allowpopups="false"
/>
```

**New IPC channel `CAPTURES_GET_FILE_URL`:**

```ts
captures:getFileUrl({ captureId, type: 'mhtml' | 'html' | 'png' })
  → string  // "file:///E:/.../storage/caseId/captureId.mhtml"
```

Old `CAPTURES_GET_CONTENT` stays for `txt` and for the Source tab's legacy HTML display.

**`<webview>` requires enabling in `BrowserWindow` webPreferences:**

```ts
webPreferences: {
  ...existing,
  webviewTag: true,
}
```

Safe with our `javascript=no` + `sandbox=yes` + `nodeIntegration=no` configuration.

**Format detection:**

```tsx
const isMhtml = capture.format === 'mhtml'
{isMhtml ? <MhtmlWebview ... /> : <HtmlIframe ... />}
```

**Source tab:**
- Legacy HTML: unchanged.
- MHTML: raw MIME source in `<pre>`, display-truncated at ~500KB with "Open file" button for full view.

**Screenshot tab:** unchanged.

**Text tab:** unchanged.

**Metadata tab:** displays new forensic fields (tool/extension/browser version, user agent, operator id/name, manifest index, prev hash, entry hash) and a "Verify integrity" button.

**Navigation lockdown:** `<webview>` handles `will-navigate` to prevent navigation and `new-window` to prevent popups. The captured page is evidence — users cannot click out.

## 10. Operator Identity & Settings

**Two new settings fields (settings key/value store):**

| Key | Type | Purpose |
|---|---|---|
| `installationId` | string (UUID v4) | Stable per-install identifier; generated on first launch, never changes |
| `operatorName` | string? | Human-friendly investigator name, optional, user-editable |

**`installationId` lifecycle:** `settings.getOrCreateInstallationId()` generates via `crypto.randomUUID()` on first call, persists, never regenerated.

**`operatorName` lifecycle:** set by user in Settings → Identity. Empty by default. Dashboard shows a non-blocking nudge banner if unset. Changes apply to future captures only; existing manifest entries are frozen.

**Exposure to capture pipeline:** the server stamps `installationId` and `operatorName` onto every capture at the server layer (extension doesn't know them). Extension sends `browserVersion`, `extensionVersion`, `userAgent` (browser-side); server adds `installationId`, `operatorName`, `toolVersion` (Electron-side).

**New UI component `src/renderer/components/settings/IdentityConfig.tsx`:**

                   (read-only)

Placed in Settings view between `StorageConfig` and `About`.

## 11. Integrity Verification UI

**Per-capture ("Verify integrity" on Metadata tab):**

```
Integrity
─────────────────────────
Content hash   a7b2c…                             ✓ Verified
Manifest entry #42   entry: c9f4…   prev: b5e1…   ✓ Chain intact
                                                   [Re-verify]
```

Re-verify streams the `.mhtml` file, recomputes SHA-256, compares to stored `captures.hash`, manifest entry's `contentHash`, and walks the full chain from index 0 through the entry.

**Per-case ("Verify chain" on `CaseOverview`):**

```
Evidence chain
─────────────────────────
Captures logged:   247
Deletions logged:  3
Chain status:      ✓ Intact through entry #250
Last verified:     2026-04-05 14:23 UTC          [Verify now]
```

Broken chain shows the offending index + expected vs actual hash.

**New IPC channels:**

```ts
captures:verifyIntegrity({ captureId })
  → { contentValid, chainValid, brokenAt?, expectedHash?, actualHash? }

cases:verifyManifest({ caseId })
  → {
      totalEntries, captureCount, deletionCount,
      valid, brokenAt?, expectedHash?, actualHash?,
      firstEntry?: string, lastEntry?: string
    }
```

## 12. Error Handling & Edge Cases

**Non-capturable pages:** `chrome://`, `chrome-extension://`, Chrome Web Store, PDF viewer, strict-CSP pages, tabs closed mid-capture. `saveAsMHTML` rejects → background posts to `POST /api/captures/errors` with `reason: 'mhtml-unavailable'`. Capture Activity shows failure with tooltip. No fallback format.

**URL scheme validation:** `http:`, `https:`, `file:`, `ftp:` attempt MHTML; everything else short-circuits with `'unsupported URL scheme'`.

**Size overruns:** streaming write enforces 200MB hard cap. On exceed: abort mid-stream, delete partial file, no DB row, no manifest entry, return 413 with `reason: 'size-limit-exceeded'`.

**Partial failures:** write-ahead manifest append paired with a synchronous DB transaction (§7.5). If the DB write fails, manifest is truncated back to its pre-append length as compensation and the MHTML file is deleted. If the process crashes between steps, startup verifies manifest tail against DB and truncates dangling entries with an audit warning. Invariant: **`manifest.jsonl` and `captures` table never disagree for committed entries**.

**Concurrent captures:** per-case async mutex prevents interleaved manifest entries.

**Manifest corruption:**
- Hand-edited → verification surfaces mismatch, flags broken entry, no auto-repair.
- File deleted externally → next append creates new manifest at index 0 with `reason: 'manifest-reset-detected'`. Loud, visible gap.
- DB/manifest drift at startup → dashboard banner: "Audit log inconsistency detected for case X."

**Extension disconnect mid-capture:** HTTP POST interrupted → Hono body parser fails → 400 → extension retries once on network error, then posts to `/api/captures/errors`.

**Settings not set:** `operatorName: null` is valid in manifest entries. No blocking behavior.

**Legacy capture deletion:** still records a `deletion` event in the manifest with `format: 'html'` on the target.

## 13. Testing Strategy

**Unit tests (Vitest):**

| Target | What's tested |
|---|---|
| `hash.ts` | Streaming `hashBuffer` matches non-streaming; hash stability |
| `manifest.ts` | Chain correctness; tamper detection at beginning/middle/end; deletion events chain correctly; canonical JSON determinism |
| `storage.ts` | Streaming write respects size cap; cleans partial files on overrun |
| `captureServer.ts` | Multipart parsing; missing fields → 400; oversize → 413; error endpoint records activity |
| `database.ts` | Migration v10 adds columns with correct defaults; legacy rows survive |
| `settings.ts` | `getOrCreateInstallationId` idempotent |

**E2E tests (Playwright):**

1. **Fake-extension E2E** — test helper posts realistic multipart requests to Hono server; verifies file, DB row, manifest entry, UI, viewer.
2. **MHTML viewer E2E** — fixture `.mhtml`, viewer mounts `<webview>` to `file://` URL, JS disabled.
3. **Verification UI E2E** — capture → verify ✓; tamper on disk → verify ✗ with correct broken index.
4. **Deletion audit E2E** — delete → assert `deletion` entry → chain still verifies.
5. **Legacy capture compatibility E2E** — seeded legacy HTML capture opens in iframe viewer.

**Fixtures (`tests/fixtures/mhtml/`):**
- `simple-page.mhtml` — minimal MHTML with text + inline CSS + inline image
- `large-page.mhtml` — ~5MB
- `oversized-page.mhtml` — 250MB generated on demand

**Not tested:** `chrome.pageCapture.saveAsMHTML()` itself, `<webview>` visual fidelity, court admissibility.

**Manual QA checklist** in `docs/testing/mhtml-capture-manual-qa.md`:
- Real page with images/CSS/fonts → offline open → exact replica
- Logged-in page → session state preserved
- SPA (Twitter/X timeline) → final rendered state
- Large image-heavy page → size cap behavior
- Tamper test → ✗ with details

## 14. Research Basis

Design grounded in the following standards and practices:

- **US FRE 901(b)(9)** — authentication via evidence that a process/system produces accurate results. Birdbrain must document its capture pipeline (tool version, operator, browser, process) such that an expert witness can explain and defend it.
- **US FRE 902(13)/(14)** (2017 amendments) — machine-generated records and hashed digital copies as self-authenticating with qualified certification.
- **US FRE 1002** — best evidence rule; MHTML as "output that accurately reflects the information" is stronger than plain screenshots (which have been rejected in e.g. *Edwards v. Junior State of America Foundation*).
- **UK ACPO Good Practice Guide v5, Principle 3** — audit trail must allow an independent expert to reproduce the result.
- **ISO/IEC 27037:2012** — preservation of original form, documented chain of custody, validated tools, repeatable processes.
- **NIST SP 800-86** — four-phase forensic process (Collection → Examination → Analysis → Reporting).

**Why MHTML specifically:**
- Self-contained single-file artifact is easy to hash, sign, archive, present.
- MIME headers preserve `Snapshot-Content-Location` (URL), `Subject` (title), `Date` (UTC), `From` (capture engine).
- Links and layout preserved; reconstructable DOM.
- Chromium's Blink engine has the serialization built in → widely understood, reviewable process → supports FRE 901(b)(9).

**Industry comparison:** Hunchly, Pagefreezer, WebPreserver, FAW all use MHTML or WARC + SHA-256 + per-capture metadata. Hunchly's explicit limitation — locally-held GPG keys — would be defeated by RFC 3161 trusted timestamps, which we scope out of this build but can add later as a premium feature.

**Future scope (not included):**
- RFC 3161 trusted timestamps from an external TSA
- Additional chain event types (case created, tag applied, case exported, manifest exported)
- WARC output format support
- PGP signature generation

## 15. Out of Scope

- RFC 3161 trusted timestamping (Tier 3 forensics)
- Re-capture workflow for existing flat-HTML captures
- Additional chain event types beyond capture + deletion
- PGP signing of MHTML files
- Court-admissibility certification or legal opinion
- MHTML format validation beyond presence of MIME headers
