# Case retrieval pipeline

**Status:** Draft
**Date:** 2026-10-02
**Audience:** Maintainer and implementers. This design describes proposed behavior, not shipped behavior.

## Problem

An Operator reduced a long-running Case to a checkable package by turning Notes into claims, checking each against its Capture, finding missing links in a chain of claims, and citing Exhibits in the final documents. An unannotated Capture held a decisive mail header, unnoticed, for much of that time. A Selector could have found its account identifier only if the Operator had known what to ask for. Extracted Text also missed facts held in image `href` attributes, while one Note made a claim its Capture did not support. Exports from AI tools carried unreliable citations and were discarded. These are distinct retrieval, extraction, and claim-check failures; a search rank cannot resolve all three. The local workflow brief at `~/handoffs/2026-09-05-case-consolidation-workflow-brief.md`, especially steps 2–4 and 6–10, records the process. Landing that brief is a separate handoff. Its live Case must never become fixture data.

Today, a Capture's Extracted Text is a Derived File on disk, mirrored in `capture_texts`; triggers maintain `captures_fts`. `searchCaptures()` in `src/main/services/db/captureRepo.ts` returns ranked Capture rows, without a locatable span. `rebuildFts()` in `src/main/services/db/dbAdmin.ts` heals the database copy from the disk file. The present full-text table covers title, URL, and Extracted Text; it does not make links hidden in raw HTML searchable. These statements describe the current Capture path. They make no claim about document or Staging Pool search. [CONTEXT.md](../../CONTEXT.md) and `src/main/services/db/migrations.ts` define the source and index relationship.

## Constraints

- **Every hit is a pointer.** A result carries the Case and internal Exhibit identifiers, the human-facing Exhibit Number, the Exhibit's Content Hash, a representation and locator, and a short preview. An internal identifier lets a client resolve the row; an Exhibit Number is what the Operator cites. The preview and any generated wording are never citable on their own. A result that cannot resolve to current stored bytes is unavailable, not a plausible-looking citation. [CONTEXT.md](../../CONTEXT.md), [ADR-0023](../adr/0023-exhibits-are-the-unit-of-evidence.md).
- **The original and the computation remain distinct.** The search cache records each source Exhibit and Content Hash, extractor version, and parameters. A separately persisted result computed from one Exhibit would be a Derived File with a Derivation; a Case-wide lookup cache is not a citable evidence object. Retrieval must not rewrite an original or promote a Note or model output to evidence. [ADR-0004](../adr/0004-adopt-osint-assurance-baseline.md), [ADR-0023](../adr/0023-exhibits-are-the-unit-of-evidence.md).
- **Exclusion precedes new indexing.** The Operator declares classes barred from search before a new Case-wide build. Excluded material is absent from new link/header fields and any future embedding payload; a later exclusion removes those entries before the next query. Current `captures_fts` already indexes every Capture's text, so this rule cannot claim that previously indexed bytes were never stored. Every existing FTS query must filter excluded Exhibits, and the maintainer must decide whether policy changes also rebuild `captures_fts` without those rows. Deleting index rows does not promise erasure from SQLite free pages, write-ahead logs, backups, or prior exports; retention and storage purge need a separate policy. Search eligibility is separate from permission to include an Exhibit in an Evidence Package. The current model has no settled exclusion-class field: ADR-0023 defers sensitivity and access labels, while [#543](https://github.com/thebristolsound/birdbrain/issues/543) presently asks about Persona disclosure, not a complete exclusion policy. This dependency needs its own decision before implementation.
- **Staging Pool content stays apart.** Pooled text may be searched only inside the Staging Pool view, marked "not anchored." Case-wide results, `exhibit.search`, claims, and Evidence Packages omit it until commit. A Working Copy may include pooled files only by opt-in. [ADR-0024](../adr/0024-a-staging-pool-outside-the-chain.md).
- **No accidental disclosure or contact.** Retrieval and indexing run locally. A search never contacts a target, Wayback, or a model provider. Any future networked inference would separately require explicit disclosure, minimization, authorization, and recorded lineage under [ADR-0004](../adr/0004-adopt-osint-assurance-baseline.md); its traffic would also have to obey [ADR-0032](../adr/0032-route-app-egress-but-do-not-disguise-the-browser.md)'s Egress and fail-closed rule. This design does not recommend remote Case-text processing.
- **Custody stays truthful.** Operator remains the human; Persona is a separate provenance axis. Read-only search writes no Manifest Entry. An agent may request reads, but no search tool gains chain-writing power or silently attributes agent action to the Operator. [ADR-0030](../adr/0030-persona-is-a-provenance-axis-beside-operator.md), [#548](https://github.com/thebristolsound/birdbrain/issues/548).

## Options and recommendation

| Approach                                      | Wins                                                                                                                                                                             | Loses                                                                                                                                                                                                                                             |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Extend local full-text and exact-field search | Finds identifiers, phrases, nearby terms, mail headers, URLs, link targets, and explicit contradictions; keeps ranking and review explainable; reuses SQLite already in the app. | Needs an Operator query or a curated discovery view; cannot infer a conceptual connection expressed with unrelated words. Full-text search can split email addresses or miss punctuation, so exact-field matching still matters.                  |
| Add local embedding search beside full-text   | May suggest a Capture that discusses a claim in different words, even when no Selector names it. Could help find candidates for a weak joint or summary citation.                | A short account-bearing header may rank poorly under an unknown query; embeddings cannot repair a missed `href` or establish that a Note is true. Model packaging, platform support, rebuild time, disk use, and evaluation become ongoing costs. |
| Add retrieval plus generated answers          | Could condense many candidates for review.                                                                                                                                       | Repeats the worked Case's citation-poisoning risk and crosses the boundary from finding material to writing the story. A fluent answer can hide an unsupported sentence.                                                                          |

**Recommend exact-span retrieval first, without generation.** Extend the local searchable representation to the raw fields Extracted Text omitted, then add fielded search, phrase and proximity queries, and a review view for unannotated Captures and identity-bearing headers. SQLite [FTS5 supports phrase and `NEAR` queries, snippets, and external-content indexes](https://www.sqlite.org/fts5.html). A snippet helps a reader choose a hit, but is not a stable offset into the stored bytes. Preserve a separate locator that can be checked against those bytes. Test exact identifiers with punctuation using field-specific matching rather than assuming FTS word splitting is sufficient.

Keep local embeddings as a candidate only after the first slice has measured misses that matter to the three workflow tasks. If a synthetic evaluation shows improved discovery at acceptable privacy, package, and review cost, add embeddings as a second ranking path over the same eligible, locatable representations. Record the exact model, version, word-splitting rules, dimensions, chunk parameters, runtime, and source Content Hash in the local build metadata. If vector data is later persisted as a Derived File, its Derivation must also carry the output hash and one parent Exhibit. Select a maintained model and runtime against primary project sources at that later decision; this draft chooses neither. A remote model is not a fallback when local inference is unavailable.

Do not generate claim text or chain documents in this pipeline. The Operator writes them. Retrieval supplies candidates; an exact check over the target Exhibit's representations and stored bytes supplies a check result that may be a miss or ambiguity. This preserves the local workflow brief's candidate B and K boundary. An AI-origin Exhibit, if the Operator later admits one to the Case, must carry an explicit classification and appear with a warning in eligible results; it must never be silently treated as corroboration. ADR-0023's current `origin` values do not identify AI exports, so classification and default exclusion are prerequisites, not a property this spec assumes already exists. [ADR-0023](../adr/0023-exhibits-are-the-unit-of-evidence.md).

### Representations and locators

Build search-only field records in the existing SQLite database when Extracted Text lacks a needed field. Do not export those records or treat them as Derived Files. If a representation is later persisted as its own file, ADR-0023 requires a Derivation under one parent Exhibit. Keep the following fields distinct, so a result can say where it came from:

| Parent                                  | Search unit and locator                                                                                                                                                                                                                                                               | Check against stored bytes                                                                                                                                                                                                                                                                                        |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture                                 | Extracted Text passage; title and URL; a decoded HTML part's visible text, link target, image alt text, and relevant document or mail headers. Locator names the captured part and a byte range where possible, otherwise the parser version and a reproducible field path plus span. | Compare the Exhibit's Content Hash, reopen the stored Capture, decode the named part with the recorded rules, and locate the same field. A text-file offset alone is not an HTML-byte offset. A Transaction Record can add observed HTTP headers only when that record exists; do not reconstruct absent headers. |
| PDF document                            | Page and text span, plus metadata field when relevant.                                                                                                                                                                                                                                | Reopen the stored PDF at the recorded Content Hash; rerun the recorded extractor or inspect the named page and field. A page-text span is not a claim that the PDF contains identical UTF-8 bytes.                                                                                                                |
| Usenet `mbox` document                  | Message ordinal or stable message key, header field, or body span.                                                                                                                                                                                                                    | Read the stored `mbox` again at the recorded Content Hash with the same parser version and locate the message and field. A standalone account-bearing mail header remains an independently searchable unit.                                                                                                      |
| Note (query input, not a retrieval hit) | Note identifier and text span can supply a claim or query.                                                                                                                                                                                                                            | Resolve any suggested support to a separate Exhibit and Content Hash. An unanchored Note yields no citable result by itself.                                                                                                                                                                                      |

For a headers-only Exhibit, index only the acquired header and directory-listing fields, with an explicit "body not acquired" result label. No body text or inferred facts are available. This kind is proposed by the workflow brief's candidate D; [ADR-0023](../adr/0023-exhibits-are-the-unit-of-evidence.md) does not define it. Link targets and alt text should preserve the exact source value and a normalized search value; normalization must never replace the value shown during source inspection.

An exact check first verifies that the requested Exhibit and Content Hash still match the stored original, then reopens the relevant representation and byte source. It reports `present`, `absent`, or `cannot-check` with the reason and locator. A check over decoded text reports that text relationship; one over raw bytes reports the byte relationship. Neither proves that the source's assertion is true or that another Exhibit corroborates it. Retrieval rank never becomes a claim status. [ADR-0004](../adr/0004-adopt-osint-assurance-baseline.md) and the local workflow brief define this boundary.

### Storage, deletion, and export

For the lexical first slice, keep `captures_fts` in the existing SQLite database and add field-specific link and header records there. Query both paths under one Case and apply the same eligibility filter. Policy changes remove new field records; old `captures_fts` rows require a separate rebuild or query-time exclusion as described in the constraints. This avoids a second copy of every Capture's Extracted Text. If embeddings later pass evaluation, prefer a separate local file per Case for vectors and build metadata, scored in the app for a bounded Case before choosing a vector extension. An extension inside the main SQLite database would speed large similarity queries but would add a native dependency and tie vector format and Case deletion to the main schema. Benchmark the bounded approach before accepting that cost. The per-Case vector file stays outside Evidence Packages, Working Copies, and Case Archives; rebuild it from eligible stored objects after Case Archive import. Deleting a Case removes that file with the Case directory and the existing database rows through their normal path; it writes no per-Capture deletion entries, consistent with [ADR-0001](../adr/0001-case-delete-skips-manifest.md). [ADR-0010](../adr/0010-evidence-package-vs-working-copy.md) distinguishes the two export classes; [ADR-0024](../adr/0024-a-staging-pool-outside-the-chain.md) governs pooled files.

This rejects one constraint in the handoff: it calls the index itself a Derived File with a Derivation. A single Case-wide index has many parent Exhibits, while accepted ADR-0023 defines a Derived File and its Manifest Entry with **one** parent Exhibit and Content Hash. `captures_fts` already shows the distinction: it is a derived index over Extracted Text that can be rebuilt, not a Manifest-anchored Derived File. The proposed link/header indexes and any later vector file likewise record local build metadata and do not enter the Manifest's integrity claims. If the maintainer instead wants a Case-wide index manifested, an ADR must add multi-parent, Case-level Derivations and define their rebuild, deletion, and export semantics.

## Smallest first slice

The first slice should let an Operator declare search exclusions, build link and header cache fields for eligible Captures, and search them within one Case alongside existing Extracted Text. Results open the exact Exhibit span and display its Content Hash and Exhibit Number. A review view should surface eligible Captures without Notes or Persisted Matches, grouped by fields such as `From`, `Reply-To`, link target, and rare account identifiers. The Operator can inspect the candidate and run the exact check before using it in a claim or chain document. This slice uses no model, vector extension, remote call, generated prose, or new public API.

That mail header would be surfaced only if its captured bytes contain a readable header, the Capture is eligible, and the Operator reviews the surfaced candidate. Neither full-text nor embeddings ensure discovery of an unknown fact. The first slice costs a one-time parse of eligible existing Captures, extraction for each new Capture, field-index storage and query joins, an exclusion policy and locator UI, and the Operator's review time. Measure its added index bytes per Exhibit, full and incremental build time on a synthetic Case of comparable size, search latency, number of candidates an Operator must inspect, and false or missed locators. Do not assign invented savings to the worked Case.

## Consumers and evaluation

Start in the app's Case search UI. After [#547](https://github.com/thebristolsound/birdbrain/issues/547) and [#358](https://github.com/thebristolsound/birdbrain/issues/358) settle the local API and Model Context Protocol (MCP) boundary, expose the same read operation as `exhibit.search`, with Case scope, eligibility filtering, bounded result counts, and pointer-plus-locator output. It must not reuse the extension's Capture Server as an unreviewed general API. A future claim-check flow may use hits only to propose target Exhibits, then run the local workflow brief's candidate B exact text-and-byte check. Chain-document authoring may attach checked Exhibit citations to Operator-written joints; it must not turn ranking into an asserted citation. [#358](https://github.com/thebristolsound/birdbrain/issues/358).

Evaluate on a synthetic Case, never on the live investigation. Include at least: a fact present only in an image link target; an unannotated mail header whose account identifier is unknown to the initial query; a Note whose target Capture lacks its phrase; a PDF page and `mbox` header with locators; a headers-only Exhibit with no body; a pooled file; an excluded Exhibit declared both before and after indexing; and an AI-origin document with a false citation. Record, per task, whether the correct Exhibit appears in the top five and top twenty, whether every shown span resolves at the stated Content Hash, false suggestions, exclusion leakage, and review time. Compare existing `captures_fts`, the extended lexical slice, and any later local embedding candidate on the same queries and eligibility rules. Hold out wording variants so the evaluation does not repeat an indexed phrase. A false citation or excluded-content result fails the safety gate regardless of recall.

## Open questions for the maintainer

1. What marks an Exhibit or Tag as excluded from search and export, and who may change that decision after indexing? Should AI-origin material be excluded by default until explicitly admitted?
2. Should Case-wide indexes remain disposable local caches, or should Birdbrain amend ADR-0023 to support a manifested multi-parent Case-level Derivation?
3. Which raw fields may appear in a search preview or MCP response when a Case contains Operator identifiers or a Persona? How will that response be disclosed without exposing the human identity that [#543](https://github.com/thebristolsound/birdbrain/issues/543) protects?
4. What measured gain on the synthetic Case would justify shipping a local embedding model, its runtime, and rebuild cost? Which operating systems and offline conditions must the first such model support?

## Decisions needed before implementation

- Record the search exclusion and AI-origin classification policy, including late exclusions, cache purge, and export behavior; reconcile it with ADR-0023 and #543 without silently rewriting either.
- Record the retrieval cache boundary in a new ADR that cites ADR-0023 and the existing `captures_fts` precedent. A manifested Case-wide index would require an explicit multi-parent amendment or superseding ADR.
- If a local embedding path passes evaluation, record its model and runtime, build metadata or Derivation fields as appropriate, platform limits, retention, rebuild, and known-answer validation under ADR-0004. A remote path would additionally reopen ADR-0032's Egress and disclosure consequences.
- Resolve #548's actor axis before any agent-triggered chain write or generation that records an authored claim. Read-only `exhibit.search` does not decide who may commit an Exhibit or export an Evidence Package.
