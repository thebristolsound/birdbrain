## Case revision trigger cost, 2026-10-17

Every write to a run input pays for one trigger and one change-log row (ADR-0042, Consequences).
This section times the two operations the plan names, a whole-Case reprocess and a Case Archive
import, and the field build the app starts after an import, with and without the triggers.

### Method

- The Case is the 1,000-Capture synthetic Case that `pnpm eval:retrieval --eval-captures=1000`
  builds in `out/retrieval-eval/profile`, built with this change at schema 40.
- `pnpm eval:retrieval --eval-phase=revision-cost` (`scripts/retrieval-eval/revisionCost.ts`)
  copies that profile fresh for every run. On the copy without triggers it removes every
  `*_revision_*` trigger with `DROP TRIGGER`, a change made to that copy only. It then exports the
  Case to an archive, untimed, and times `reprocessCase()`, `importCaseArchive()` of that archive,
  and `ensureCaseFields()` on the imported Case, as the import handler starts it.
- Five runs per variant, alternating the two variants run by run. Change-log rows are counted as
  the rows `case_change_log` gained during each operation.
- Machine: Intel Core Ultra 5 125H, Linux 7.2.5, Electron 44.7.0 (Node 24.21.0), SQLite 3.53.4.
  The runs were not isolated from other work on the machine.

### Results

| Operation | With triggers, median | Without, median | With triggers, each run (s) | Without, each run (s) | Change-log rows per run |
| --- | --- | --- | --- | --- | --- |
| Whole-Case reprocess | 35.7 s | 34.8 s | 63.5, 35.7, 24.0, 37.3, 25.0 | 31.2, 35.3, 31.8, 34.8, 79.8 | 19,174 |
| Case Archive import | 5.0 s | 9.4 s | 6.0, 5.0, 4.6, 4.7, 11.0 | 9.8, 5.6, 7.2, 9.4, 9.6 | 10,386 |
| Field build after the import | 27.0 s | 16.3 s | 16.3, 14.4, 28.6, 27.0, 42.5 | 13.6, 16.3, 28.7, 12.5, 39.9 | 1,000 |

The full report is `out/retrieval-eval/revision-cost.json`, regenerated by the command above.

### What the measurement shows

- The row counts are exact and repeat on every run: a reprocess of the Case writes 19,174
  change-log rows, an import 10,386, and the field build after it 1,000, one per Capture.
- The times do not separate the triggers' cost from run-to-run variation. Within each variant the
  slowest run of an operation took 1.7 to 3.2 times as long as the fastest. For every operation
  the two medians differ by less than the spread of the noisier variant, and for the import the
  copy without triggers had the slower median. These runs therefore show no trigger cost large
  enough to stand out at this Case size on this machine, and they do not measure a smaller one.
- A measurement that isolates the triggers' share needs a machine with no other load, or a
  benchmark of the database writes alone.
