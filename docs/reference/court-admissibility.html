Court Admissibility

Chain of custody, integrity, and trusted time — what Birdbrain proves about a web capture, how it proves it, and the limits stated plainly.

In this set: Overview Exporting evidence Verifying evidence

This is the reference document for Birdbrain's court-admissibility feature: the set of controls that let a web capture be offered as evidence and independently re-verified by a third party. It is written to be citable by counsel or an expert declarant, and detailed enough for an engineer or opposing technical reviewer to audit the implementation.

It is deliberately honest about what each control does not prove. Over-claiming is what gets digital evidence excluded; the value of this design is that every claim it makes is reproducible with stock tools, and every limit is stated up front.

1. What Birdbrain proves — and what it does not

Birdbrain reports two separate, orthogonal axes. Conflating them is the usual way a chain-of-custody argument gets muddied, so the tool keeps them apart everywhere — in the data model, the UI, the export, and the verifier.

AxisQuestion it answersMechanism
IntegrityHave the captured bytes and the audit trail survived intact, unaltered since capture?SHA-256 content hash + a hash-linked, per-entry RSA-signed manifest
Trusted timeDid this content provably exist no later than time T, attested by an independent third party?RFC 3161 timestamp token from an external Time-Stamping Authority (TSA)

A byte-perfect capture is integrity-verified whether or not it carries a trusted timestamp. Lacking a timestamp is not an integrity failure — it is simply an empty (or pending) trusted-time axis.

1.1 The integrity claim

Every capture's content is hashed with SHA-256 at capture time, and that hash is recorded in an append-only, hash-linked, per-entry-signed manifest (manifest.jsonl). Any later alteration — to a captured file, to a hash, or to a chain link — is detectable: the altered entry no longer hashes to its recorded entryHash, its signature no longer validates, and re-hashing one entry breaks every downstream link.

1.2 The trusted-time claim

Where enabled, a capture's content hash is submitted to an external RFC 3161 TSA, and the returned timestamp token is retained inside the signed manifest. Because the token is issued and signed by a third party over the content hash, it establishes that the captured bytes existed no later than the stamped time — a fact the operator cannot back-date or forge regardless of their control over the local machine.

1.3 The honest limits (read before citing anything)

These limits are stated plainly so that no brief, declaration, or marketing claim over-states what the tool establishes. The design embraces them rather than papering over them.

  1. The signing key is installation-local — not an independent trust anchor. The per-entry signature is made with an RSA-2048 keypair generated on the operator's own machine; the public half ships inside the evidence package. It raises the bar against casual tampering (copying a case folder and editing it with ordinary tools fails verification), but it does not defend against a determined operator running Birdbrain's own code, who controls the key and could in principle mint a fresh, internally consistent chain. This is an inherent limit of any locally-held key. The RFC 3161 timestamp is the independent anchor that closes this gap, for timestamped captures.
  2. Operator identity is self-asserted. The certifier name, role, and organization recorded in an export are entered by the operator and are not cryptographically authenticated. Birdbrain does not verify the operator's real-world identity.
  3. The TLS certificate chain is corroboration, not binding. When recorded, it is re-fetched from the origin after the capture is stored — it corroborates that the origin served a matching certificate around capture time, but does not prove it is the exact certificate served on the captured transaction. See ADR-0002.
  4. A programmatic/binary PASS is an integrity result, not a timestamp-authenticity proof. The standalone verifier checks timestamp tokens structurally (the token's message imprint binds the content hash, and the token bytes match the signed manifest). It does not verify the TSA's CMS signature. That canonical check is openssl ts -verify in the by-hand runbook. So binary-PASS ≠ runbook-PASS: a forged token (correct imprint, invalid TSA signature) passes the binary and is caught only by openssl ts -verify.
  5. The Certificate of Authenticity is scaffolding for counsel. Birdbrain generates an FRE 902(13)/(14) supporting certification with the factual fields filled in, but the operative sworn/declaration wording must be supplied by counsel for the relevant jurisdiction and rule. See §2.11.

2. The chain-of-custody architecture

Each capture flows through a fixed pipeline, and each piece below contributes one verifiable fact to the record. The numbering is a reading order, not a runtime order (timestamping and TLS corroboration happen out of band, after storage).

2.1 Capture and content hashing

A page is captured by the Chrome extension as a self-contained MHTML archive (forensic format) and transmitted to a local HTTP server inside the Birdbrain desktop app. On receipt the server computes the SHA-256 digest of the captured bytes — this is the capture's contentHash, the anchor every other control binds to. The bytes are written to disk and the metadata recorded in SQLite. Full pipeline details are in the capture pipeline reference.

Alongside the MHTML, a viewport screenshot (PNG) and the page's extracted text (.txt) are stored when available. Both are independently hashable (see §2.7).

2.2 The signed, hash-chained manifest

Every case directory contains a manifest.jsonl — an append-only audit log, one JSON object per line, that is the cryptographic root of trust for everything in that case. It records four kinds of entry, discriminated by type:

Entry typeRecordsKey fields
captureA page was capturedcaptureId, url, timestamp, contentHash, optional screenshotHash / textHash / headers / tls, sizeBytes, operator identity
timestampAn RFC 3161 token was obtained for a capturecaptureContentHash, timestamp, tsaToken (base64 DER)
deletionA capture was deletedcaptureId, contentHash, optional reason
exportAn evidence package was producedpackageHash, verificationResult

Every entry, regardless of type, carries the same chain machinery:

  • index — a 0-based sequence number that increments by exactly 1 per entry.
  • prevHash — the entryHash of the immediately preceding entry (empty string for the first entry). This is the hash link.
  • schemaVersion — currently 2. v2+ entries must carry a valid signature; legacy v1 entries predate signing and are grandfathered as integrity-only.
  • entryHash — SHA-256(canonicalStringify(body)), where body is the entry with entryHash and signature removed (see §2.3).
  • signature — an RSA-SHA256 (PKCS#1 v1.5) signature over the entryHash hex string, base64-encoded (see §2.4).

Excluding both entryHash and signature from the hashed body is load-bearing: it keeps the hash recomputable by a third party and ensures the signature (which covers the hash) never participates in the hash it covers.

Tamper detection follows from three independent properties:

  • Edit a body field → the recomputed entryHash no longer matches → fail.
  • Forge or strip a v2 signature → signature verification fails → fail.
  • Re-hash one entry to cover an edit → its entryHash changes → the next entry's prevHash no longer links → every downstream entry fails.
Write-ahead durability

Appends are transactional: the manifest line is written and fsync'd before the side effect it records (file writes, DB insert), and rolled back (truncated to the prior byte offset) if that side effect fails. The manifest therefore never records a capture, deletion, or export that did not actually happen.

2.3 Canonical serialization

To hash an entry, its body must serialize to the same bytes for Birdbrain and for any independent verifier. canonicalStringify provides that:

  • Object keys sorted (JavaScript default — UTF-16 code-unit order).
  • undefined properties dropped; no insignificant whitespace.
  • Primitives serialized via JSON.stringify.

This is JCS-shaped (RFC 8785) but intentionally not a conformant JCS implementation. It deliberately does not Unicode-normalize string values — RFC 8785 §3.1 also forbids altering string data, and forensically the tool must hash exactly what was captured. Cross-tool determinism instead rests on two manifest invariants, guarded by tests:

  • Entry keys are fixed ASCII schema names, so JS code-unit sort, Unicode code-point sort, and the runbook's jq -cS codepoint key sort are all byte-identical.
  • Chained numeric fields are integers, so JSON.stringify and jq -c emit the same minimal form.

The single shared implementation is bundled byte-identically into the standalone verifier (asserted by the binary's --self-check golden-vector mode), so the app and the verifier cannot drift. The canonical, court-facing recompute path is the runbook recipe (jq -cS + sha256sum), not an off-the-shelf JCS library.

2.4 The installation signing key

On first run Birdbrain generates an RSA-2048 keypair:

  • Private key — PKCS#8 PEM, wrapped at rest with the OS credential store (DPAPI on Windows, Keychain on macOS) via Electron safeStorage, stored as signing-key.pem. If the OS credential store is unavailable at load time, Birdbrain fails closed — it refuses to start signing rather than silently regenerating a key, which would invalidate every previously signed entry.
  • Public key — SPKI PEM, stored in plaintext as signing-public-key.pem and bundled into every export.

Signatures are RSA-SHA256 / PKCS#1 v1.5 over the entryHash hex string, base64-encoded — the exact claim that stock openssl dgst -sha256 -verify checks. Birdbrain never hand-rolls signature verification; the verify-core and openssl check the same bytes.

2.5 RFC 3161 trusted timestamping

Trusted time is obtained out of band, never on the capture's critical path:

  1. Request. Birdbrain builds a DER-encoded RFC 3161 TimeStampReq whose message imprint is the capture's contentHash (a SHA-256 digest), with a 64-bit random nonce for replay protection and certReq=true so the TSA embeds its signing certificate — making the returned token self-contained and offline-verifiable.
  2. Send. The request is POSTed to the configured TSA (Content-Type: application/timestamp-query), with a 30-second timeout. The response's PKIStatus must be granted/grantedWithMods.
  3. Bind & record. The returned token is parsed; its message imprint must equal the capture's content hash (rejecting a misissued or mismatched token). A type: 'timestamp' manifest entry is appended carrying the base64 DER token — signed and chained like every other entry.
Default TSA: DigiCert

http://timestamp.digicert.com. The rationale (see the threat model): the DigiCert Trusted Root G4 is present in essentially every OS/browser trust store, so openssl ts -verify succeeds offline against a root the verifier already trusts; the endpoint is unauthenticated (no account, works on first run); and it is the de-facto timestamp authority behind much of Authenticode code-signing. The TSA is configurable in Settings for engagements requiring a specific authority. Free/hobbyist TSAs are a documented dev/test fallback only — their roots are not in common trust stores.

The asynchronous worker. Captures are enqueued (trusted-time state pending) and stamped by a background worker that runs on capture, on app start, and on a 5-minute retry interval. Offline degradation is simply "no timestamp entry yet" — the capture still succeeds and stays pending until a later attempt lands. The worker guards against double-stamping a capture whose token arrived concurrently.

The canonical verification of a token's TSA signature is openssl ts -verify against the TSA chain — Birdbrain never hand-rolls CMS/PKCS#7 crypto. In-app and in the binary, timestamp handling is structural only (imprint match + byte binding); see §2.12.

2.6 The trusted-time axis

Every capture resolves to one of three trusted-time states, derived from the manifest alone (the SQLite mirror column is a rebuildable cache, reconstructable from the manifest at any time):

StateMeaningHow it is reached
rfc3161A TSA token attests this capture's content hashA timestamp entry references the contentHash and its token imprint matches
pendingAn eligible capture awaiting its tokenA v2 capture entry with no matching timestamp entry yet
noneA grandfathered legacy capture that predates timestampingA v1 entry, or no capture entry

A verified capture is never none (verified ⇒ v2 ⇒ pending or rfc3161). pending vs none is the eligibility distinction: v2 captures are expected to be stamped; legacy v1 captures never were.

2.7 Sidecar integrity — screenshot and extracted text

The screenshot (PNG) and extracted text (.txt) are bound to the chain by their own SHA-256 hashes, recorded as the optional screenshotHash and textHash fields on the capture entry — signed and chained exactly like contentHash. These fields are omitted entirely (never empty-string or null) when absent, so legacy and no-screenshot entries keep their original canonical bytes and chain hashes.

In an evidence package the screenshot is content-addressed: its filename is its SHA-256 (screenshots/{sha256}.png), so identical screenshot bytes across captures resolve to one file, and the file is self-describing. At verification, the package PNG is bound to the chained, signed screenshotHash — not merely to the unsigned index.

2.8 HTTP response headers

When the capture carries them, the page's HTTP response headers are anchored into the capture entry (headers), normalized to lowercase keys with multi-value joins for deterministic serialization. Like the sidecar hashes, the field is omitted when absent so legacy/headerless entries' chain hashes are unchanged.

2.9 TLS certificate-chain corroboration

When recorded, the serving TLS certificate chain is captured as origin corroboration (tls on the capture entry): subject, issuer, validity window, SHA-256 fingerprint, serial number, and subject alternative names for each cert in the chain, plus the re-fetch URL and timestamp.

Corroboration, not binding

This is obtained by a tls.connect() re-fetch from the desktop app after the capture is stored — it is not bound to the specific captured HTTP transaction. It establishes that, seconds to minutes after capture, the origin was reachable and serving a matching, trust-store-valid certificate. It does not prove that this is the same certificate served on the captured response (a cert rotation, CDN failover, or redirect in the interval could differ). Both the capture and re-fetch timestamps are recorded so a reviewer can judge the interval. Present these fields to a court as corroboration, never as binding origin proof. Rationale and the deferred binding-mode design are in ADR-0002.

2.10 The evidence package (export)

Export produces a single self-contained, stored (uncompressed) ZIP — the artifact handed to opposing counsel or the court. Its layout:

FileRole
manifest.jsonlThe signed, hash-linked audit chain — root of trust
signing-public-key.pemRSA public key for the per-entry signatures
tsa-ca-chain.pemTSA CA root + each token's embedded cert chain
pages/{captureId}.mhtmlCaptured content (hashed as contentHash)
screenshots/{sha256}.pngScreenshot, content-addressed (hashed as screenshotHash)
timestamps/{captureId}.tstRFC 3161 tokens (DER), when present
report.htmlHuman-readable case report
certification.htmlFRE 902(13)/(14) supporting certification (see §2.11)
evidence.jsonUnsigned convenience index — reconcile, do not trust
VERIFY.mdThe by-hand verification runbook (stock tools, zero Birdbrain code)

Two facts about the package matter for verification:

  • evidence.json is not signed. Only manifest.jsonl is. The verifier therefore treats the verified manifest chain as the sole source of truth and reconciles the index against it — an attacker who edits only the index (drops a capture, rewrites a digest, bumps the head) is caught by re-deriving everything from the chain.
  • The package commits to its own contents via packageHash. packageHash = SHA-256(canonicalStringify(sortedArtifacts)), where sortedArtifacts is every packaged file's {path, sha256, sizeBytes} ordered by path. It deliberately does not hash the final .zip or evidence.json itself — that would be circular, since packageHash is recorded into a signed export entry that is itself bundled in the package.

Exports are themselves chained. After the ZIP is written, Birdbrain appends a signed type: 'export' entry to the live case manifest, recording packageHash and the integrity verificationResult (capture / verified / tampered / missing counts). This makes the production of evidence packages part of the same tamper-evident audit trail. As a consequence the bundled manifest.jsonl lags the live manifest by exactly this one entry, by design — packageHash commits to artifact content, not to the entry it informs.

2.11 The Certificate of Authenticity (FRE 902(13)/(14))

certification.html is a supporting certification scaffold aimed at Federal Rules of Evidence 902(13) (records generated by an electronic process) and 902(14) (data copied from an electronic device, verified by hash). Birdbrain fills in the factual fields:

  • Capturing tool name and version, and hash algorithm (SHA-256).
  • A plain-language description of the capture-and-hash process.
  • The configured RFC 3161 TSA.
  • The certifier (operator name, role, organization, installation ID).
  • A trusted-time summary and per-capture timestamped / non-timestamped tables.
Two honesty controls built into the document

Identity is self-asserted — the certifier fields are entered by the operator and are not cryptographically authenticated. And a [LEGAL WORDING TO BE SUPPLIED BY COUNSEL] banner marks that the operative sworn declaration / certification language (e.g. the 28 U.S.C. § 1746 attestation) for the applicable jurisdiction and rule is not drafted by the tool. Counsel must supply it. Do not treat the scaffold as finalized legal text.

2.12 Independent verification

Verification logic lives in a process-agnostic verify-core (src/shared/verify/): pure modules that depend only on Node fs/crypto/path, zod, and @peculiar/asn1-* — no Electron, database, network, or app code. The desktop app imports it directly; the standalone binary bundles the same modules, so app-vs-verifier drift is impossible by construction.

Three verification surfaces consume it:

  1. In-app verification — the desktop app re-hashes captures and re-checks the chain on demand (the case's integrity bar). See §3.
  2. The standalone binary / CLI (birdbrain-verify) — a prebuilt, per-OS Node SEA single-executable that runs the full package verifier against an unzipped package and reports PASS/FAIL with a specific reason per check. It is fs+crypto only (the build asserts no Electron/native/network imports leaked in). A binary PASS means integrity + internal consistency, not timestamp authenticity (see §1.3, limit 4).
  3. The by-hand runbook (VERIFY.md, shipped in every package) — reproduces the full integrity claim with only sha256sum, openssl, and jq, including recomputing entryHash from the entry body and the canonical openssl ts -verify TSA check.

The complete procedure for all three is in Verifying evidence.

3. Reading verification results

3.1 Integrity status (per capture)

The in-app verifier and the audit trail report one integrity status per capture:

StatusMeaning
verifiedThe MHTML bytes re-hash to the stored contentHash, the manifest chain is valid, and every recorded sidecar hash (screenshot/text) re-binds.
tamperedThe recomputed content hash differs from the signed value, or a recorded sidecar hash no longer binds. The primary evidence does not match the chain.
chain-brokenThe manifest hash chain failed to verify (a recompute / linkage / signature break somewhere in the case).
missingThe capture's MHTML file is unreadable or absent.
legacyA pre-MHTML / non-forensic capture with no chain coverage to verify.

3.2 Trusted-time state (per capture)

Reported independently of integrity: rfc3161, pending, or none (see §2.6). For rfc3161, the TSA identity and the asserted stamp time are surfaced alongside.

The two axes are always shown separately. A verified + pending capture is byte-perfect but not yet third-party-timestamped; a verified + rfc3161 capture is the strongest state — unaltered and anchored in time by an external authority.

5. Limits and caveats, consolidated

For quick reference when preparing a declaration or responding to a challenge:

  • Local signing key defeats casual tampering, not a determined operator running the app; the RFC 3161 timestamp is the independent anchor for stamped captures (§1.3, §2.4).
  • Operator identity is self-asserted, not authenticated (§1.3, §2.11).
  • TLS chain is corroboration, not binding to the captured transaction (§2.9).
  • Binary PASS ≠ runbook PASS: the binary checks timestamps structurally; the canonical TSA-signature check is the runbook's openssl ts -verify (§1.3, §2.12).
  • The 902(13)/(14) certificate is scaffolding — counsel supplies the operative legal wording (§2.11).
  • Trusted time is best-effort and asynchronous: an offline or in-flight capture is pending, not failed; export is never blocked on it (the package warns about unstamped captures instead).
